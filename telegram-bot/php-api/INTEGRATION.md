# Интеграция бот-API в qmods.ru

Эта папка содержит **дополненные версии** двух уже существующих на сайте
файлов плюс один новый файл. Ничего не переписано с нуля — старые действия
(`ping`, `plans`, `me`, `link`, `stats`, `users`, `user`, `payments`,
`issue`, `remove`, `delete_user`, `notifications`, `send_notification`)
работают точно так же, как раньше. Добавлены только новые действия для
разделов бота «Устройства», «Уведомления» и push-доставки.

## Что и куда положить

| Файл в этом репозитории | Куда на сервере |
|---|---|
| `mod/includes/bot_notify.php` | `mod/includes/bot_notify.php` (**новый** файл) |
| `mod/api/bot.php` | заменяет существующий `mod/api/bot.php` |
| `mod/admin/bot.php` | заменяет существующий `mod/admin/bot.php` |

`bot_notify.php` использует только уже существующие функции из
`includes/bootstrap.php` (`load_users`, `update_users`, `load_notifications`,
`update_notifications`) — отдельного хранилища пользователей не создаётся,
всё пишется в тот же `data/notifications.json` и `data/users.json`.

## Токены

В обоих файлах есть константа `BOT_API_TOKEN_HASH` со значением-заглушкой
`PASTE_..._HASH_HERE`. Сгенерируйте **два разных** токена через
`mod/admin/generate_token.php` (по одному на пользовательский и на
админский API — не используйте один и тот же токен для обоих):

1. Откройте `https://qmods.ru/mod/admin/generate_token.php` (он уже есть на
   сайте), скопируйте `TOKEN` и `HASH`.
2. `HASH` вставьте в `BOT_API_TOKEN_HASH` соответствующего файла.
3. `TOKEN` (сам секрет, не хеш!) сохраните в секреты воркера:
   ```bash
   wrangler secret put QMODS_BOT_API_TOKEN        # для mod/api/bot.php
   wrangler secret put QMODS_ADMIN_BOT_API_TOKEN   # для mod/admin/bot.php
   ```
4. Удалите `generate_token.php` с сервера после использования (как и
   написано в самом файле).

⚠️ Если в старых бэкапах/архивах сайта мог "засветиться" прежний токен или
хеш — считайте его скомпрометированным и сгенерируйте новый, а не
переиспользуйте старый.

## Где вызвать `notify_user_event()`

Чтобы события сайта долетали и в кабинет (колокольчик), и в бота, добавьте
по одному вызову в уже существующие обработчики событий. Функция не создаёт
новых сущностей — она просто пишет обычное персональное уведомление в
`data/notifications.json`, которое затем:
- показывается в кабинете (уже работает "из коробки", ничего доделывать не
  нужно);
- забирается кроном воркера через `pending_telegram_pushes` и уходит в
  Telegram.

### 1. Успешная оплата — `subscribe/notify.php`

Файл уже подключает `includes/telegram.php` и зовёт `tg_notify_payment()`
(это админский алерт, не трогаем). Добавьте рядом персональное уведомление:

```php
require_once dirname(__DIR__) . '/mod/includes/bot_notify.php'; // добавить в require в начале файла

// ...после строки: tg_notify_payment($username, $amount, $plan['title']);
notify_user_event(
    $usernameLower,
    '💰 Оплата прошла успешно',
    "Подписка «{$plan['title']}» активирована. Спасибо!"
);
```

### 1.1. Алерт админу об оплате — «кто/когда/что купил»

Отдельно от уведомления покупателю (выше) — сообщение **вам** (владельцу
проекта) в Telegram при каждой успешной оплате. Работает независимо от
`tg_notify_payment()`, если он уже что-то шлёт — эта очередь не пересекается
с ней, доставляется тем же cron'ом воркера (раз в 5 мин) на все
`ADMIN_TELEGRAM_IDS`. В том же месте `subscribe/notify.php`:

```php
notify_admin_payment_event(
    $usernameLower,
    $plan['title'],
    $amount,
    (int)($plan['days'] ?? 0)
);
```

Сообщение придёт в формате:
```
💰 Новая оплата

Пользователь: username (id 5110155633)
План: Про · 30 дн.
Сумма: 299 ₽
Дата: 27.08.2026 14:32
```
`id` рядом с username — это `telegram_id`, если аккаунт привязан к Telegram
(кликабелен как `<code>`, удобно скопировать); если не привязан — просто
username без id.

### 2. Окончание подписки — уже автоматизировано

`mod/includes/reminders.php::run_expiry_reminders()` уже создаёт персональные
уведомления с `target = username` при приближении окончания подписки — они
автоматически попадут и в бота благодаря `bot_notify.php`, доп. код не
нужен. Единственное дополнение — само уведомление получит поле
`sent_via_telegram` (добавляется автоматически при первом обращении к
`get_pending_telegram_pushes()`), не влияет на текущую логику `read_by`.

### 3. Привязка устройства

На сайте сейчас нет отдельного события "устройство привязано" — устройство
регистрируется неявно (при первом входе из приложения). Если такое событие
появится, добавьте туда:

```php
notify_user_event($usernameLower, '📱 Новое устройство', 'Устройство успешно привязано к аккаунту.');
```

Отвязка устройства **через бота** уже уведомляет пользователя — это сделано
в `mod/api/bot.php` (`action=device_remove`), ничего дополнительно делать не
нужно.

### 4. Новости проекта

Рассылка всем делается из самого бота (`/admin` → «📣 Рассылка всем») —
она уже вызывает `notify_broadcast_event()` через
`mod/admin/bot.php?action=send_notification` без параметра `target`.
Дополнительно вызывать что-либо на сайте не требуется.

## Deep-link привязка — открывать бота с уже готовым кодом

⚠️ **Известный баг в текущем `cabinet.php` (не только в этом разделе, но и
в `change_password`/`add_review`)**: `render_header()` выводит flash-тосты
(`get_flashes()`) сразу в начале `<main>`, ещё до любой секции с `id`. Если
редирект после действия несёт `#anchor` (например `redirect('cabinet.php#profile')`),
браузер при загрузке страницы мгновенно прокручивает её к этой секции —
мимо тоста, отрисованного в самом верху. Тост не мелькает, он просто вне
экрана с первого кадра. Из-за этого пользователь, нажавший «Получить код
привязки», не видит ни код (при успехе), ни текст ошибки (при сбое) —
страница просто «молча» перезагружается. Патч ниже это заодно чинит для
`create_telegram_link` (успешный путь вообще не показывает флеш — сразу
уходит в бота; путь с ошибкой возвращает `redirect('cabinet.php')` **без**
`#profile`). Тот же однострочный фикс (убрать `#profile` из `redirect()`)
стоит сделать и в `change_password`, и в `add_review`, если там тоже не
видно тостов.

По умолчанию `cabinet.php` после генерации кода просто показывает его во
флеш-сообщении, и пользователь вводит его в боте руками. Вместо этого можно
сразу открывать чат с ботом: Telegram поддерживает диплинки вида
`https://t.me/<bot_username>?start=<payload>` — по такой ссылке бот получает
`/start <payload>` первым же сообщением. Воркер уже умеет это (см.
`worker/src/handlers/router.ts`): если payload имеет вид `link_<КОД>`, бот
сразу пытается привязать аккаунт этим кодом, без ручного ввода. Как приятный
побочный эффект — этот путь вообще перестаёт зависеть от видимости тоста.

В `mod/cabinet.php` найдите обработчик `action === 'create_telegram_link'`
(там же, где код генерируется — `$code = strtoupper(...)`) и замените блок
после `update_users(...)`:

```php
// Было:
if ($ok) {
    flash('success', 'Код для Telegram: ' . $code . ' — действует 10 минут.');
} else {
    flash('error', 'Не удалось создать код для Telegram.');
}
redirect('cabinet.php#profile');
exit;
```

на:

```php
// Стало:
if (!$ok) {
    flash('error', 'Не удалось создать код для Telegram.');
    redirect('cabinet.php'); // БЕЗ #profile — иначе тост не будет виден, см. предупреждение выше
    exit;
}

// Сразу открываем чат с ботом — код уходит как /start-параметр,
// вводить его руками не нужно. Замените qmods_bot, если юзернейм бота другой.
redirect('https://t.me/qmods_bot?start=link_' . $code);
exit;
```

По желанию — обновите текст кнопки чуть ниже (в блоке `<summary>🤖 Telegram`)
с «🤖 Получить код привязки» на «🤖 Открыть бота и привязать аккаунт», чтобы
подпись соответствовала новому поведению.

### Если не хотите сразу переходить на deep-link — минимальный фикс

Только убрать `#profile`, оставив остальную логику (текст с кодом) как есть:

```php
if ($ok) {
    flash('success', 'Код для Telegram: ' . $code . ' — действует 10 минут.');
} else {
    flash('error', 'Не удалось создать код для Telegram.');
}
redirect('cabinet.php'); // было: redirect('cabinet.php#profile');
exit;
```

Старый способ (набрать `/link` в боте и прислать код текстом) продолжает
работать как запасной вариант — ничего в боте для этого менять не нужно.

## Предложить привязку Telegram при входе в кабинет (миграция в бота)

Цель — постепенно перевести всех пользователей с личного кабинета сайта на
бота: там же оплата, устройства, уведомления и поддержка, но без отдельного
пароля и с мгновенными пушами. Ничего не отключается принудительно — сайт
продолжает работать как есть, это именно **напоминание**, которое пропадает
само, как только у пользователя появляется `telegram_id`.

⚠️ Это работает только для входа через **веб** (`login.php` без
`device_id`). Вход из приложения уходит через `app_callback.php?...&app=1`,
а по комментарию в самом файле это приложение перехватывает ещё до
рендера HTML — серверная подсказка там физически не будет показана.
Показать её в приложении можно только изменив само Android-приложение —
там уже есть свой отдельный путь привязки (кнопка «Войти через Telegram» /
«Подтвердить по юзернейму» на экране входа, см. `android-client/README.md`
раздел «Привязка по юзернейму»), сайт-баннер его не заменяет и не дублирует.

### 1. Тост сразу после входа

В `mod/login.php` найдите успешный веб-вход (после блока с редиректом на
`app_callback.php`, перед `redirect('cabinet.php')`):

```php
// Было:
            if ($device_id !== '') {
                redirect('app_callback.php?status=ok&username=' . urlencode($user['username']) . '&expires_at=' . $sub['expires_at'] . '&app=1');
            }
            redirect('cabinet.php');
```

```php
// Стало:
            if ($device_id !== '') {
                redirect('app_callback.php?status=ok&username=' . urlencode($user['username']) . '&expires_at=' . $sub['expires_at'] . '&app=1');
            }
            if (empty($user['telegram_id'])) {
                flash('info', '🤖 Управляйте подпиской быстрее — привяжите Telegram-бота QMods: оплата, устройства и уведомления в одном чате, без пароля. Это займёт 30 секунд.');
            }
            redirect('cabinet.php');
```

Веток с `redirect()` до этой точки не выполняется дальше (`redirect()` сам
делает `exit`), поэтому проверка `$device_id !== ''` тут не нужна — до неё
просто не доходит выполнение при входе из приложения. Тост показывается на
**каждом** веб-входе, пока `telegram_id` пуст — специально без троттлинга
(раз в день/раз за сессию и т.п.), чтобы не потерять пользователей, которые
заходят редко.

### 2. Постоянный баннер в кабинете, пока не привязано

Раздел «Telegram» в `cabinet.php` сейчас спрятан в свёрнутый `<details>` —
именно из-за этого его было не найти в прошлый раз. Добавьте баннер над
уже существующим «Нужна помощь?» (`class="support-cta support-cta-top"`,
там же используется `<a href="support.php">`):

```php
<?php if (empty($user['telegram_id'])): ?>
<a class="support-cta support-cta-top" href="#telegram"
   onclick="var d=document.querySelector('#telegram details'); if (d) d.open = true;"
   style="background:linear-gradient(135deg,#3157ff,#7c3aed)">
    <span class="support-cta-icon">🤖</span>
    <div><b>Привяжите Telegram-бота</b><small>Подписка, устройства, оплата и уведомления — прямо в чате, без пароля от сайта</small></div>
    <strong aria-hidden="true">→</strong>
</a>
<?php endif; ?>
```

`id="telegram"` стоит на обёртке `<section>`, а не на самом `<details>`,
поэтому браузер сам его не раскрыл бы (`:target` работает только когда
`<details>` — предок цели, а тут наоборот) — отсюда `onclick`, который
раскрывает блок явно. Баннер пропадает автоматически, как только
`telegram_id` появится у пользователя.

Раздел `#telegram` уже поддерживает deep-link привязку (см. выше
«Deep-link привязка») — после клика по баннеру пользователь на мобильном
сразу попадает в диалог с ботом с готовым кодом, без ручного ввода.

### 3. Необязательно: мягкий «дедлайн» в копирайте

Если понадобится дожать оставшихся пользователей сильнее, чем нейтральное
«привяжите», не меняя код — достаточно один раз отредактировать текст в
шаге 1/2 (например, сослаться на дату, когда часть функций кабинета станет
доступна только через бота). Технически ничего для этого доделывать не
нужно: `telegram_id` у уже привязанных пользователей никак не меняется, а
у непривязанных баннер/тост продолжат показываться как обычно.

## Выключатель входа/регистрации на сайте

Часть миграции пользователей на Telegram-аккаунты (см. `README.md`
«Миграция на Telegram-аккаунты»): админ включает/выключает это одной
кнопкой в `/admin` бота («🌐 Вход/регистрация на сайте»), состояние —
`data/site_auth_gate.json` (`get_site_auth_gate`/`set_site_auth_gate` в
`bot_notify.php`). По умолчанию (файла ещё нет) вход/регистрация
**включены** — деплой одного только `bot_notify.php` ничего не меняет на
сайте, пока вы не добавите проверку в сами формы и пока админ явно не
выключит их из бота.

⚠️ **`login.php` и `register.php` — это ЕЩЁ и точка входа для мобильного
приложения** (через `?device_id=...`: автологин по устройству в
`login.php`, привязка пробного периода к устройству в `register.php`,
обе завершаются редиректом в `app_callback.php`). **Старое приложение
умеет входить/регистрироваться ТОЛЬКО через эти страницы** — у него нет
кода для привязки через бота (это появилось в более новых сборках, см.
`android-client/README.md`), поэтому «мин. версия приложения»
(принудительное обновление через `/device/subscription`) для него не
работает — старая сборка физически не умеет спрашивать `/device/subscription`,
она вообще не знает о существовании воркера/бота. Значит для
`device_id !== ''` нужен ДРУГОЙ экран, чем для обычного браузера:
не «идите в бота» (`render_site_auth_gate_block()`), а «обновите
приложение» (`render_update_required_block()`) — и, если человек в
данный момент как раз авторизован (аккаунт нашёлся по `device_id` и
подписка активна), эта функция не разлогинивает его и сразу же
показывает код/диплинк привязки Telegram, чтобы он успел привязать
аккаунт, пока ещё сидит в устаревшем приложении.

⚠️ **Обычная ссылка `https://t.me/...` не откроет Telegram изнутри WebView
старого приложения** — WebView просто грузит её как страницу внутри себя,
Android не резолвит http(s)-ссылки во внешний intent автоматически (для
этого нужен код в самом приложении — `shouldOverrideUrlLoading`, которого
у нас нет). `render_update_required_block()` вместо этого использует
`intent://resolve?...#Intent;scheme=tg;package=org.telegram.messenger;
S.browser_fallback_url=...;end` — специальный синтаксис, который парсит
сам Chromium (на нём работает системный Android WebView): просит ОС
открыть `org.telegram.messenger`, а если Telegram не установлен —
сам открывает `browser_fallback_url` (обычную `t.me`-ссылку) вместо
ошибки. Работает без единой правки кода самого приложения. Подробнее:
https://developer.chrome.com/docs/multidevice/android/intents. Плюс под
ссылкой всегда виден код для ручного ввода в боте (с кнопкой «📋
Скопировать») — на случай если и `intent://` почему-то не сработает
(WebView совсем без Chromium-движка, урезанная intent-фильтрация и т.п.).

**В `mod/register.php`** — сразу после того, как `$device_id`/`$client_ip`
уже вычислены (следующие две строки в файле уже существуют, добавьте
проверку сразу за ними). Тут привязывать нечего — при `register.php`
аккаунта ещё не существует, поэтому `render_update_required_block()`
вызывается без аргумента:

```php
$device_id = trim((string)($_REQUEST['device_id'] ?? ''));
$client_ip = trim((string)($_SERVER['REMOTE_ADDR'] ?? ''));

// ↓ добавить:
require_once __DIR__ . '/includes/bot_notify.php';
if (!get_site_auth_gate()['enabled']) {
    if ($device_id === '') {
        render_site_auth_gate_block();
    }
    render_update_required_block(); // старое приложение — предложить обновиться
}
```

**В `mod/login.php`** — два отдельных места:

1. После существующей строки
   `if (is_logged_in() && $device_id === '') redirect('cabinet.php');`
   (порядок важен: уже залогиненных браузерных пользователей сначала
   пропускаем в кабинет как обычно, а не показываем им блок-экран):

   ```php
   if (is_logged_in() && $device_id === '') redirect('cabinet.php');

   // ↓ добавить:
   require_once __DIR__ . '/includes/bot_notify.php';
   if ($device_id === '' && !get_site_auth_gate()['enabled']) {
       render_site_auth_gate_block();
   }
   ```

2. Внутри ветки автологина по устройству — **после** того, как сессия уже
   установлена (`session_regenerate_id`/`$_SESSION[...]`), но **до**
   `redirect('app_callback.php?...')`, чтобы не разлогинить человека, а
   просто не пускать его дальше в старое приложение:

   ```php
   if ($beh === 'autologin' && $u) {
       $sub = subscription_info($u);
       if ($sub['active']) {
           session_regenerate_id(true);
           $_SESSION['user_id'] = (string)$u['id'];
           $_SESSION['username'] = (string)$u['username'];

           // ↓ добавить (после установки сессии, до редиректа в app_callback.php):
           require_once __DIR__ . '/includes/bot_notify.php';
           if (!get_site_auth_gate()['enabled']) {
               render_update_required_block($u);
           }

           redirect('app_callback.php?status=ok&username=' . urlencode($u['username']) . '&expires_at=' . $sub['expires_at'] . '&app=1');
       }
   }
   ```

   ⚠️ **Этой одной проверки НЕДОСТАТОЧНО** — если у вас используется
   конструктор-«вредитель» из `includes/shutdown.php` (`cfg()`,
   `login_behavior()`), при обычном `cfg()['mode'] === 'off'`
   `login_behavior()` возвращает `'form'`, а не `'autologin'` (см. её код —
   `case 'cycle'/'squeeze'/'random'/'shadow'` дают `'autologin'`/`'error'`,
   всё остальное, включая `'off'`, падает в `default: return 'form';`).
   Это значит, что в обычном режиме (без специально включённого сбоя)
   проверка выше **практически никогда не сработает** — выполнение
   провалится сквозь весь блок `if ($device_id !== '') {...}` прямо к
   обычной форме пароля ниже, а там раньше не было гейта вообще. Поэтому
   нужен ещё один перехват — **сразу после закрывающей `}` всего блока**
   `if ($device_id !== '') {...}`, ловящий любой непрерванный исход (в
   первую очередь `'form'`, а заодно `'autologin'` с неактивной
   подпиской):

   ```php
   if ($device_id !== '') {
       $u = find_user_by_device(load_users(), $device_id);
       $beh = login_behavior($c, $u, $device_id);
       if ($beh === 'block') page_block($c['message']);
       if ($beh === 'error') page_error();
       if ($beh === 'update') page_update();
       if ($beh === 'autologin' && $u) {
           /* ...как в пункте выше... */
       }

       // ↓ добавить — основной перехват для старого приложения:
       require_once __DIR__ . '/includes/bot_notify.php';
       if (!get_site_auth_gate()['enabled']) {
           render_update_required_block($u ?? null);
       }
   }
   ```

   `$u` может быть `null` (устройство ещё не знакомо, например при первом
   запуске приложения) — `render_update_required_block()` это учитывает и
   просто не показывает блок привязки Telegram, если привязывать нечего.

`require_once` во всех местах безопасен при повторном подключении — PHP
не подключит файл дважды, если он уже был подключён этим же путём раньше.

### `api/check_device.php` — уже открытое приложение (не только заход на login.php)

Всё выше перехватывает только МОМЕНТ входа/регистрации. Но старое
приложение, уже находясь внутри (пользователь давно залогинен, сессия
живёт неделями), **не перезаходит на `login.php` само по себе** — поэтому
`site_auth_gate` его не достанет, пока не сработает что-то ещё.

Это «что-то ещё» уже есть в проекте: `mod/api/check_device.php` — plain-text
хартбит (`OK`/`NO_SUB`/`KICKED`), который приложение **периодически
опрашивает, уже работая** (это и есть тот единственный канал, через
который конструктор-«вредитель» из `includes/shutdown.php`
(`cfg()['mode'] === 'kicked'`/`'full'`) реально «достаёт» уже открытые
сессии — сам конструктор ни `cabinet.php`, ни что-либо ещё не трогает).
Раз это единственный проверенно рабочий канал — используем тот же самый,
уже понятный приложению статус `"KICKED"`, вместо того чтобы придумывать
новый, который приложение не умеет разбирать:

```php
$device_id = $_GET['device_id'] ?? '';
if ($device_id === '') { echo "ERROR"; exit; }

// ↓ добавить — сразу после этой строки, ДО $c = cfg(); и любой логики
// конструктора, чтобы миграционный гейт работал независимо от того, что
// сейчас настроено в /admin/shutdown.php:
require dirname(__DIR__) . '/includes/bot_notify.php';
if (!get_site_auth_gate()['enabled']) {
    echo "KICKED";
    exit;
}

$c = cfg();
```

⚠️ В проекте также есть `api/status.php` (JSON: `active`/`expired`/`no_auth`)
— он проверяет только `is_shutdown()` (глобальный `mode === 'full'`), НЕ
завязан на `cfg()`/`should_kick()`/таргеты, то есть режим `'kicked'`
конструктора его не трогает вообще. Если не уверены, какой из двух
эндпоинтов реально опрашивает установленная у пользователей версия
приложения (может быть один, могут быть оба) — патчите оба на всякий
случай тем же принципом; лишний `if (!get_site_auth_gate()['enabled'])`
безвреден для эндпоинта, который приложение не использует.

Итого при выключенном гейте: обычный браузер без `device_id` видит
«идите в бота»; старое приложение при заходе на `login.php`/`register.php`
(`device_id !== ''`) в любом сценарии видит «обновите приложение» (плюс
код/диплинк привязки Telegram, если аккаунт уже активен, без
разлогинивания); уже открытое приложение с активной сессией ловит это же
на следующем опросе `check_device.php` — получает `"KICKED"`, что (как и
раньше для режима `'kicked'` конструктора) заставляет его вернуться на
`login.php`, где сработает уже описанная выше логика. Уже вошедших через
сессию браузерных пользователей (открытый `cabinet.php`) ничего из этого
не трогает.

⚠️ Не путайте с разделом выше («Предложить привязку Telegram при входе в
кабинет») — тот показывает мягкое напоминание непривязанным пользователям
*после* успешного входа, этот раздел — жёстко блокирует сам вход/регистрацию,
когда админ явно выключил их из бота. Обычно достаточно только первого,
пока миграция не близка к завершению.

## Ничего не сломается, если интеграцию не делать

Все перечисленные вызовы `notify_user_event()` — не обязательны для работы
бота: разделы «Профиль», «Подписка», «Устройства», «Оплата» всегда читают
актуальные данные напрямую из `data/users.json` через уже существующий
`action=me`. Без интеграции просто не будет **проактивных** пуш-уведомлений
об оплате — пользователь всё равно увидит актуальный статус подписки, зайдя
в раздел «⭐ Моя подписка».
